# ACT 模型推理全流程记录：从 tract-onnx 到 ncnn INT8 量化优化

日期：2026-05-05 至 2026-05-09

## 概述

目标：在 StarryOS RISC-V QEMU 256MB 内存限制下运行 ACT（Action Chunking Transformer）模型推理。ACT 模型是一种模仿学习模型（ResNet-18 骨干 + 8 层 Transformer Encoder + 4 层 Transformer Decoder），用于双臂精细操作，输入 (1,3,224,224) 图像 + (1,2) 状态向量，输出 (1,8,2) 动作序列。

核心约束：荔枝派 SG2002（RISC-V，256MB 内存）。模型文件需在 256MB 限制内加载并执行推理。

---

## 阶段一：tract-onnx — ONNX 推理初步验证（5/5）

### 背景

首个推理框架选型：tract（Rust 生态的 ONNX 推理引擎）。目标是在 StarryOS RISC-V QEMU 上验证 ONNX 模型推理的可行性。

### 实现

1. 使用小模型 `simple.onnx`（571KB，14 元素输出）做初步验证
2. 随后升级为 ACT 模型的简化版本（输入 64x64，非 224x224），支持动态 axes
3. 测试程序 `tract-hello`（Rust，`tract_onnx` crate）
4. 12 个测试用例交叉验证：
   - zeros 输入 → 验证全零输入的确定性输出
   - ones 输入 → 验证全壹输入的确定性输出
   - 10 组随机输入 → 与 Python 参考输出交叉验证（max_err < 0.001）

### 测试配置

```toml
# qemu-riscv64.toml
shell_init_cmd = "/usr/bin/tract-hello"
memory = 512M
timeout = 120s
```

### 结果

- 模型加载：tract 解析 ONNX → 优化图 → 构建 runnable，均在 StarryOS 上完成
- 12 个测试用例全部 PASS
- 单次推理 ~数十 ms（小模型）

### 经验

- tract 可以直接在目标平台上加载和优化 ONNX 模型，无需预先编译
- 但 tract 对动态 axes 和 ResNet 风格模型支持有限，且不支持 INT8 量化
- tract 模型加载内存占用高（Rust 的 tract 运行时本身消耗大），不适合 256MB 平台

---

## 阶段二：ONNX Runtime（ORT）交叉编译（5/7）

### 背景

从 tract 切换到 ONNX Runtime（C API），原因是：
- ORT 更成熟，支持 INT8 量化
- C API 内存占用更可控
- ORT 支持 ORT 格式模型（优化后的二进制格式）

### 实现

1. 交叉编译 ONNX Runtime 到 RISC-V：
   - 禁用 `COMPILE_WARNING_AS_ERROR`
   - providers 从 shared 改为 static library
   - 添加 `-Wno-error` 跳过警告
2. 模型导出：PyTorch ACT 模型 → ONNX（`act_model.onnx`，193MB）→ ORT 格式（`act_model.ort`，188MB）
3. 测试程序 `ort_test.c`（C 程序，调用 ONNX Runtime C API）
4. QEMU 内存需提升到 1024MB（初次验证用）

### 结果

- ORT 模型加载和推理在 1024MB QEMU 上成功 PASS
- 但在 512MB 下 OOM（模型 188MB，ORT 运行时 + 模型加载 + 中间张量 总内存 >512MB）

### 关键发现

- `zero_copy_for_initializers` 选项导致 COW 页错误内核 panic（ORT 的权重张量被标记为只读，但 ACT 模型的某些 Op 会写入输入张量）
- 必须关闭 `mem_pattern` 和 `cpu_arena` 减少内存占用

## 阶段三：Conv/BN 诊断测试 — 验证 RISC-V 推理正确性（5/8 上午）

### 背景

在 256MB 限制下探索前，需要确认 RISC-V 上的 ORT 推理浮点计算是正确的。创建三个最小化的 Conv 模型进行跨平台对比。

### 实现

1. Python 脚本 `create_conv_models.py` 生成三个 ONNX 模型：
   - `conv1x1`：1x1 Conv（GEMM 实现），input (1,2,3,3) → output (1,3,3,3)
   - `conv3x3`：3x3 Conv（im2col+GEMM 实现），input (1,1,5,5) → output (1,1,3,3)
   - `conv_bn`：3x3 Conv + BatchNorm，input (1,1,5,5) → output (1,2,3,3)
2. 导出为 ORT 格式，使用确定性权重和输入（`(i % 17 - 8) * 0.1` 的填充模式）
3. 同时在 x86 本地和 RISC-V QEMU 运行 `ort-conv-test`，对比输出 hex 值

### 结果

```
conv1x1 PASSED — 27/27 完美匹配（0 ULP 差异）
conv3x3 PASSED — 6/9 完美匹配，3/9 差 1 ULP
conv_bn  PASSED — 18/18 完美匹配（0 ULP 差异）
```

RISC-V 的浮点 Conv（GEMM/im2col/BN fuse）计算结果与 x86 基本一致。

### 经验

- RISC-V QEMU 的浮点计算是正确的，精度问题来自量化误差，不是硬件
- 这种确定性输入的小模型诊断方法快速有效

## 阶段四：mmap + 256MB 优化（5/8 中午）

### 背景

256MB 限制下，ORT 188MB 模型文件无法加载。尝试通过 mmap 文件映射减少拷贝开销。

### 实现

1. `mmap_test.c` 验证 StarryOS mmap 正确性（MAP_PRIVATE + fd, 16KB 文件按需分页）
2. `ort_test.c` v4 更新：关闭 mem_pattern/cpu_arena，单线程，关闭图优化
3. mmap 加载 ORT 模型：ORM 优先使用 mmap 加载，省掉 ifstream vector 拷贝

### 结果

- mmap 功能验证 PASSED
- ORT 在 512MB 下通过（堆 ~258MB + mmap ~197MB 模型）
- ORT 在 256MB 下仍然 OOM

### 经验

- ORT 的 FP32 模型（188MB）即使 mmap 加载，ORT 内部仍需为权重和中间张量分配大量堆内存
- 必须对模型进行量化压缩才能满足 256MB 限制

## 阶段五：ncnn 框架迁移（5/8 下午 - 5/9）

### 背景

从 ONNX Runtime 切换到 ncnn，原因：
1. ncnn 原生支持 FP16 存储（模型尺寸减半）和 INT8 量化
2. ncnn 内存占用小（无 heavy runtime，纯 C++ 推理）
3. ncnn 对移动端/嵌入式场景设计，内存控制更精细

### 模型转换

1. pnnx 工具链：PyTorch `.pt` → ncnn `.param` + `.bin`
2. 原始 PyTorch 权重 189MB → ncnn FP16 模型 95MB → INT8 模型 48MB

### FP16 模型内存实测（RISC-V QEMU 512MB）

```
[MEM-ncnn] start: brk=0x40022000
[MEM-ncnn] after model load: brk=0x43691000  (+54.7MB)
[MEM-ncnn] after inference: brk=0x43e86000  (+62.4MB 峰值)
```

### INT8 模型精度

| 方案 | 模型大小 | vs FP16 平均误差 | 判定 |
|------|----------|-----------------|------|
| FP16 基准 | 95MB | — | 256MB 装不下 |
| INT8（ACIQ） | 48MB | 10.04% | 误差太大 |

## 阶段六：INT8 量化精度优化（5/9）

### 方案一：逐通道权重量化 → 失败

怀疑校准表只给每个卷积层一个 scale（逐张量），改为从权重值直接计算逐通道 scale。

**结果**：48MB，平均误差 10.24%。失败原因：ncnn 原生支持逐通道权重量化，校准表的 `*_param_0` 条目已经是逐通道的。

### 方案二：更换校准方法 KL vs ACIQ → 失败

**结果**：48MB，KL 平均误差 10.70%（与 ACIQ 的 10.04% 无本质区别）。失败原因：校准方法只改变逐张量激活阈值，瓶颈不在阈值选择。

### 方案三：ResNet FP16 + Transformer INT8 → 失败

**结果**：59MB，平均误差 9.79%。失败原因：误差主要来自 Transformer 层量化，而非 ResNet。

### 方案四：ResNet INT8 + Transformer FP16 → ✅ 成功

只量化 ResNet 卷积层（`convrelu_*`、`conv_*`），Transformer 保持 FP16。

| 方案 | 模型大小 | 平均误差 | 判定 |
|------|----------|---------|------|
| ResNet INT8 + Transformer FP16 | **84MB** | **0.19%** | ✅ 最优 |

RISC-V QEMU 256MB 验证：
```
ncnn-inference (48.68s) — PASSED
输出与 x86 FP16 参考：最大误差 0.68%，平均误差 0.19%
总堆峰值 ~63MB，256MB 内充裕
```

## 所有方案对比总表

| 方案 | 模型大小 | 峰值内存 | 平均误差 | 结论 |
|------|----------|----------|---------|------|
| 全 FP16 | 95MB | ~205MB | 基准 | 256MB OOM |
| 全 INT8（ACIQ） | 48MB | 46MB | 10.04% | 误差太大 |
| 全 INT8（KL） | 48MB | — | 10.70% | 误差太大 |
| 逐通道权重量化 | 48MB | — | 10.24% | 无改善 |
| ResNet FP16 + Transformer INT8 | 59MB | — | 9.79% | 无改善 |
| **ResNet INT8 + Transformer FP16** | **84MB** | **63MB** | **0.19%** | ✅ |

## 核心经验

1. **推理框架选择至关重要**：tract → ORT → ncnn，最终 ncnn 因轻量级设计和原生 INT8 支持成为正确选择
2. **ncnn 原生支持逐通道权重量化**，校准表的 `*_param_0` 条目已经是逐通道的
3. **精度瓶颈在 Transformer（Gemm/MHA），不在 ResNet** — 反直觉但经实验验证
4. **逐张量激活量化是根本限制** — 激活量化是逐张量的（整个层一个 scale），逐通道权重量化精度够但逐张量激活量化不够
5. **选择性量化是有效的折中方案** — 对精度敏感的层保留 FP16，其余 INT8

## 待解决问题

1. Transformer Gemm/MultiHeadAttention INT8 量化的精确误差来源（`out_weight_data_int8_scale` 逐张量量化是嫌疑点）
2. 当前 84MB 模型距离全 FP16（95MB）只节省 11MB，压缩率有限
3. 逐通道激活量化是根本解决方案，但需修改 ncnn 推理内核
